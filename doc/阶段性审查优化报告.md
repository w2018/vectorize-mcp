## 0. 结论摘要

本次共形成 **24 项已确认缺陷**（P0 4 项 / P1 13 项 / P2 7 项）、**10 项待验证风险**、**25 项优化建议**，另记录 **6 项经复核排除的假象/非缺陷**。

最需要优先处理的四件事：

1. **默认 `tokenBudget=600` 使 `hit@3` 结构性等于 `hit@1`**：实测默认配置下 40 条标注查询全部只返回 1 条，把预算放宽到 1200 后 `hit@3` 从 72.5% 升到 80%。这不是检索算法不行，而是预算常量把评测指标压死了。
2. **空结果的 `request_id` 幂等缓存永不过期**：普通空搜索即可触发；`needs_review` 分支还会让事实从未落库却返回 `ok:true`。
3. **MCP 握手版本号硬编码 `0.3.9`**，而更新检查接口报 `0.4.1`，两个口径互相矛盾。
4. **错误映射三处失真**：REST 全局错误处理器丢弃 `e.message`；MCP 层把所有域错误消息压成 `"Memory operation failed"`；调度器过载被写成 `"Authorization service unavailable"`，429 限流被写成 `INTERNAL_ERROR/retryable:false`。

性能上，单次检索在 5000 条规模下线上 p50 约 **170–180 ms**、离线纯计算 p50 约 **99 ms**，随 N 近似线性增长；根因是每次检索全表 JSON 解析 + 每次命中无条件重写 FTS 索引 + 单次调用最多 4 次跨线程 `validate()`。

### 2.2 P0 详述

#### D-01【已确认缺陷】MCP 版本号硬编码，与更新检查口径冲突

`src/mcp/http.ts:91`：

```ts
{ name: "vectorize-mcp", version: "0.3.9" },
```

而 `package.json:3` 为 `"version": "0.4.1"`。另一侧 `src/server/admin.ts:1144-1152` 的 `currentVersion()` 用 `await readFile(join(installRoot, "package.json"), "utf8")` / `return String(raw.version ?? "0.0.0");` 供 `/api/v1/update/check` 使用，因此该接口报 `0.4.1`。

- 【线上实测】`initialize` 返回 `"version":"0.3.9"`。
- 影响：客户端按 `serverInfo.version` 做能力协商/缓存时会拿到错误版本；同一服务两个版本口径矛盾。（`src/mcp/bridge.ts:107,133` 的 `0.1.0` 是 stdio-bridge 独立身份，不是本服务，不计入。）

#### D-02【已确认缺陷】默认预算把 `hit@3` 结构性封顶

源码链：

- `src/core/store.ts:87-88`：`defaultLimit: 3,` / `tokenBudget: 600,`
- `src/core/store.ts:2887`：`let used = 100,`（固定开销）
- `src/core/store.ts:2892-2903`：`cost = Buffer.byteLength(JSON.stringify({...compact...}))`，`if (used + cost > budget) { exhausted = true; continue; }`
- `src/core/store.ts:2954-2967`：`ranks` 只由 **返回的 `items`** 计算，`hit_at_3: ranks.some((rank) => rank <= 3)`

默认可用预算为 `600 - 100 = 500` 字节，而单条 compact 记忆实测约 400–580 字节 → 最多放进 1 条；`limit=3` 不可达，被预算剔除的候选也不会计入 `ranks`，于是 `hit@3` 永远等于 `hit@1`，评测指标静默低估。

- 【线上实测】`bench2.ts` `B_default_600` 80 条：p50 170.3 ms / avg 171 ms / **avg_items = 1.0，items_hist 全部为 1 条** / `budget_exhausted 79/80` / 0 空结果。
- 【线上实测】`hitcap.ts` 40 条标注查询：
  - 默认 `b600_l3`：`hit_at_1 72.5` / `hit_at_3 72.5` / `avg_items 1` / `items_hist {"1":40}` / `budget_exhausted 40`
  - `b1200_l5`：`hit_at_1 72.5` / `hit_at_3 80` / `avg_items 2.58` / `items_hist {"2":17,"3":23}` / `budget_exhausted 40`
  - → 预算放宽后 `hit@3` 提升 **7.5 个百分点**，说明这是预算截断而非召回能力问题。
- 【线上实测】`units.cjs`：`dedup` 中 `estimated_tokens` 与 items 实际字节差恒为 100（`1200=1100+100`、`1040=940+100`、`887=787+100`），直接印证 `used=100`。

#### D-03【已确认缺陷】空快照幂等重放永不过期（含 `needs_review` 丢事实）

- `src/core/store.ts:4006-4031` `mutate()`：以 `(actor = tokenId+":"+subjectId, tool, request_id)` 写 `dedup`，`snapshots` 由 `result.ids` 生成。
- `src/core/store.ts:1820-1853` `replay()`：**逐条** `load` 快照并校验 `revision/status/effective`，失败抛 `SNAPSHOT_STALE`。若 `ids: []`，`snaps` 为空 → **零校验直接返回旧响应**。
- `dedup` 无 TTL，仅在 `restore` / 删账户时清理（`store.ts:981,3779,3839`）。
- `src/core/store.ts:1892-1904`：`if (similar.length && !input.distinct_reason)` → `status: "needs_review"`、`ids: []`，**在 `this.save(m)` 之前 return**，事实从未落库；但 `envelope` 仍 `ok:true`（`:1643`）。

运行时证据：

- 【离线复现】`stale-search.ts`：`EMPTY_FIRST {items:0, est:100}` → 随后新增一条匹配记忆 → `SAME_RID_AFTER_ADD` 仍是 `{items:0, est:100}`；换 `FRESH_RID_AFTER_ADD` 得到 `{items:1, est:393}`。**普通空搜索即可触发**，不限于 `needs_review`。
- 【离线复现】`needs-review.ts`（注入向量制造相似命中）：`FIRST_ADD` 返回 `needs_review` + `similar_candidates`，`TOTAL_AFTER_FIRST = 1` → 事实确实未落库；`REPLAY_SAME` 仍 `needs_review`；把种子向量换成正交向量后 `REPLAY_AFTER_STATE_CHANGE` 仍 `needs_review`（陈旧）；`FRESH_RID` 立即 `created`、`total=2`（证明状态已变、本应重新判定）。
- 补充说明（避免夸大）：`src/mcp/http.ts:145-168` 的 `needsReview` 强制 `silent=false`，故 MCP 层**保留了完整 envelope**（含 `similar_candidates`），不是响应级丢失；真正缺口是 `distinct_reason`（`src/mcp/schemas.ts:196`）既不在 `toolDescriptions.memory_add`（`:265`，写明 `Runs silently`）也不在 server instructions（`src/mcp/http.ts:94-101`），Agent 会以为已保存而不重提。
- 【边界】`needs_review` 依赖 `similar()` 读 `vectors`（`store.ts:2531-2563`），当前线上 `vectors=0` / `embeddingDimension=0`，故该分支在本次线上压测中不可达；结论来自离线注入向量复现。

### 3.4 响应速度根因归纳

1. 每次检索 `this.all()` 全表 JSON 解析 + 两次归一化 + 最多 60×N 子串扫描（D-24）。
2. 每次命中 `this.save(current, false)` 无条件重建 `memory_fts`，而该索引全仓无读取（D-24）。
3. 单次 MCP 调用最多 4 次 `validate()` + `replayWrite` + `prepareSearch` + `commitSearch`（`src/server/service.ts:181-284`），每次都是跨线程调度到 2 槽读池（D-23）。

5. 三处权重重复计算：`all()` `:1687`、`prepareSearch` `:2818`、`rank()` `:2859-2869` 又用 `HALF_LIFE` 表（14–730 天）叠加 importance×recency，与 `weight()` `:106-121` 的 `halfLifeDays=180` 是两套公式（`src/core/store.ts:106-121,1687,2818,2859-2869`）。
6. `replay` 双跑：`search()` `:2990-2991` 与 `mutate()` `:4006` 各一次。

### 4.2 总结与写入流程

**写入链路**（`src/server/service.ts:181-284` → `src/core/store.ts:1855-1944`）：

1. `:190-191` 省略 `request_id` 则每次 `randomUUID()`（无幂等）；提供文本则由 `src/mcp/schemas.ts:9-17` `toRequestId` 用 sha256 前 16 字节派生确定性 UUID。
